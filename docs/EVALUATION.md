## 1. Problem Statement

Indian merchants lose 5–15% of MRR monthly to failed payments. Existing solutions either retry blindly (wasting customer goodwill) or escalate everything (costing more than the recovery is worth). No system currently combines ML prediction, AI reasoning, cost optimization, and compliance guardrails in a single bounded workflow.

## 5. Safety & Compliance

### 5.1 Policy Engine Gates
1. Transaction state check (already recovered → STOP)
2. Retry limit enforcement (max 1 automatic retry)
3. Amount limit (₹10,000 auto-limit, above requires approval)
4. Duplicate action prevention (idempotency key)
5. Terminal failure detection (card expired → no retry)
6. Human approval for high-value transactions
7. Fraud flag → manual review only

### 5.2 Stopping Rules
- Stop if transaction recovered
- Stop if max retries exceeded
- Stop if recovery window expired
- Stop if policy check fails
- Stop if human approval rejected
- Stop if duplicate action detected
- Stop if external API non-retryable failure
- Stop if monetary limit exceeded

## 6. What Broke (Failure Recovery)

### Issue 1: Webhook Success/Failure Confusion
**What**: Razorpay emits both success and failure events on the same stream. Initially, `order.paid` events were being processed as failures.
**Detection**: Running all event types through the pipeline revealed 6 of 8 event types were never exercised.
**Fix**: Added explicit success event handling that closes receivables instead of creating them.
**Prevention**: Added event-type coverage tests.

### Issue 2: Hash Chain Empty Verification
**What**: The hash chain verification returned `True` for empty ledgers (vacuously true), masking a bug where entries weren't being written.
**Detection**: Unit test that writes an entry and then verifies the chain.
**Fix**: Changed `__bool__` on the ledger and added explicit empty-chain handling.
**Prevention**: Added regression test for empty-to-populated chain transition.

### Issue 3: Railway postgres:// URL Crash
**What**: Railway injects `postgres://` URLs but SQLAlchemy 2.0 requires `postgresql://`.
**Detection**: First database query at runtime.
**Fix**: Added URL scheme rewriting in config.
**Prevention**: Added to startup validation.
